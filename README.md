# SUSHI ROLLS — نظام إدارة مطعم ونقطة بيع

تطبيق ديسكتوب احترافي (Electron + React + TypeScript) لسلسلة SUSHI ROLLS، بواجهة عربية RTL كاملة وهوية بصرية مبنية من اللوجو الرسمي (أسود / أحمر / دهبي / أبيض)، وقاعدة بيانات Supabase هي مصدر كل الأرقام والصلاحيات.

## المكوّنات

- **Electron 32** بنافذة آمنة: `contextIsolation: true`، `sandbox: true`، `nodeIntegration: false`، وpreload محدود عبر `contextBridge`، وكل استدعاءات IPC متحقَّق منها بـZod.
- **React 18 + Vite + TypeScript + Tailwind** مع مكتبة مكوّنات خاصة بهوية العلامة (أزرار، جداول، Select، DatePicker عربي، حوارات، ⋯ menus، Toast).
- **Supabase**: Postgres + Auth + Realtime + Storage. كل الصلاحيات مفروضة على مستوى قاعدة البيانات (RLS) وليس الواجهة فقط.
- **Recharts** للرسوم، **xlsx** للتصدير Excel، طباعة إيصال 80/58مم وPDF A4 عبر Electron، نسخ احتياطي JSON.

## خطوات التشغيل (مرة واحدة)

### 1) مشروع Supabase

1. أنشئ مشروعاً جديداً على [supabase.com](https://supabase.com).
2. **لمشروع جديد** — إحدى طريقتين:
   - **من Supabase Dashboard (بدون تثبيت):** افتح **SQL Editor** وشغّل كل ملف على حدة بالترتيب: `supabase/schema.sql` ثم كل ملفات `supabase/migrations/*.sql` من الأقدم للأحدث (8 ملفات). لا تستخدم `apply-migrations.sql` هنا لأنه يستخدم `\i` الذي لا يدعمه SQL Editor.
   - **من PowerShell في مجلد المشروع** (بعد تثبيت PostgreSQL client): `psql "postgresql://postgres:[PASSWORD]@db:[PROJECT-REF].supabase.co:5432/postgres" -v ON_ERROR_STOP=1 -f supabase/apply-migrations.sql` — بدّل الرابط Connection string من **Project Settings → Database → Connection string → Direct connection**. لاحظ أن صيغة `$SUPABASE_DB_URL` المذكورة أعلاه هي لـ bash؛ في PowerShell استخدم `$env:SUPABASE_DB_URL` أو ضع الرابط مباشرة كما في المثال.
   - **لقاعدة بيانات موجودة بالفعل:** شغّل الـ 8 ملفات في `supabase/migrations/` بالترتيب فقط — **لا تُعد تشغيل `schema.sql`** (يوجد حاجز يمنع ذلك حمايةً لإصلاحات الأمان). لا يكفي `schema.sql` وحده، ولا يكفي `supabase db push` وحده لأنه لا يُنشئ الأساس. للتحقق من قائمة التحديثات شغّل `node scripts/check-migrations.mjs`.
3. من **Authentication → Providers → Email**: اقفل خيار **Confirm email** (الحسابات داخلية باسم مستخدم وليس بريداً).
4. **بعد إتمام شاشة «إعداد أول مدير»** اقفل **Allow new users to sign up** من نفس الصفحة؛ إضافة الموظفين بعدها تتم من شاشة «المستخدمين» عبر Edge Function فقط.
5. من **Settings → API** خذ `Project URL` و`anon public key` — هما الوحيدان اللازمان للتطبيق. **لا تضع service_role داخل التطبيق إطلاقاً.**

### 2) وظيفة إدارة المستخدمين (اختياري لكن مهم)

إنشاء/تعديل/حذف المستخدمين يتم عبر Edge Function تستخدم service_role على السيرفر فقط:

```bash
npx supabase login
npx supabase link --project-ref <PROJECT_REF>
npx supabase functions deploy admin-users
```

بدون نشرها: التطبيق يعمل ويسجّل الدخول، لكن شاشة «المستخدمين» ستظهر تنبيه أن الوظيفة غير منشورة.

### 3) تشغيل التطبيق

- **نسخة جاهزة:** ثبّت `SUSHI-ROLLS-Setup-1.0.30.exe` من مجلد `dist/`.
- **أول تشغيل:** شاشة «ربط قاعدة البيانات» → أدخل Project URL وanon public key واضغط «اختبار الاتصال وحفظ» → ثم شاشة إعداد أول مدير (سوبر أدمن). البيانات تُحفظ في `config.json` داخل مجلد بيانات التطبيق؛ بناء الإصدار يمكن أيضاً تضمينهما وقت البناء عبر متغيري `VITE_SUPABASE_URL` و`VITE_SUPABASE_ANON_KEY`.
- **من الكود:**

```bash
npm install
npm run dev
```

> ملاحظة: إذا ظهرت رسالة npm عن تعطيل install scripts، شغّل `node node_modules/electron/install.js` ثم `npm run dev`.

## الطباعة

- الإيصال الحراري يدعم 80مم و58مم، وتذكرة مطبخ منفصلة، وفاتورة A4 (تُحفظ PDF).
- من **الإعدادات → الطباعة** اختر الطابعة. عند اختيار طابعة يتم الطباعة الصامتة تلقائياً بعد البيع؛ بدون اختيار يظهر حوار الطباعة عند الطلب فقط.

## النسخ الاحتياطي

- **الإعدادات → النسخ الاحتياطي**: تصدير/استعادة JSON يشمل الإعدادات والمنيو والمخزون والموردين والعملاء والترابيزات والموظفين.
- الأوردرات والمدفوعات والورديات تُحفظ في نسخ Supabase التلقائية (Database → Backups).

## الإصدارات والتحديث التلقائي

- الريبو: `https://github.com/supportplix/sushi-rolls` (لازم يكون **Public** عشان التحديث التلقائي يقرأ GitHub Releases بدون توكن).
- التطبيق المثبّت بيبحث عن تحديث بعد التشغيل وبعدها كل 4 ساعات، ينزّل التحديث، ويطلب إعادة التشغيل.
- لعمل نسخة جديدة:

```bash
npm version patch
git push --follow-tags
```

- الـ workflow `.github/workflows/release.yml` يبني المثبّت و`latest.yml` وينشرهم في GitHub Releases تلقائياً **كنسخة مسودة (Draft)** عند دفع وسم `v*` فقط، بعد نجاح فحص الأنواع والاختبارات واختبارات Edge واختبار Migrations. التشغيل اليدوي من **Actions** يبني ويفحص بدون نشر.
- **التوقيع إلزامي للإصدارات:** يجب ضع `CSC_LINK` و`CSC_KEY_PASSWORD` في أسرار الريبو؛ البناء بدون شهادة يفشل في CI. لا تُزَل `publisherName` من `app-update.yml` — التحقق من الناشر في electron-updater يجب أن يظل مفعّلاً. راجع المسودة و`latest.yml` قبل نشرها للعملاء.
- ملف `.env.production` بيحتوي على Project URL وpublishable key (آمنين للنشر). ممنوع وضع `service_role` في أي ملف داخل التطبيق. لا تستخدم نفس الملف للبيئة الحقيقية والتجريبية.

### قائمة تحقق الإصدار

1. تأكد أن شجرة Git نظيفة (`git status`) — لا تُصدّر نسخة من تعديلات غير ملتزمة.
2. شغّل `npm run typecheck` و`npm test` و`node scripts/check-migrations.mjs`.
3. تأكد أن رقم `package.json` يطابق الوسم `v<version>` الذي ستدفعه.
4. تأكد أن `CSC_LINK` و`CSC_KEY_PASSWORD` مضبوطان في أسرار GitHub، وأن `publisherName` موجود في `app-update.yml` للنسخة الموقّعة.
5. بعد اكتمال الـ workflow، راجع المسودة والمرفقات و`latest.yml` ثم انشرها يدوياً.

## الحذف والاستعادة (للمالك / السوبر أدمن فقط)

- لتفعيل دي لازم تطبّق في SQL Editor بالترتيب: `supabase/superadmin_delete.sql` ثم `supabase/trash.sql` (الدالة `owner_delete` بتأرشف الصف قبل حذفه، و`owner_restore` بترجّع الدفعة).
- بعدها تظهر صفحة **إدارة الحذف والاستعادة** في القائمة للسوبر أدمن/المالك فقط. تقدر تختار أي جدول (بما فيه الأوردرات والمدفوعات) وتحذف صف، ثم تستعيده من «سجل الحذف» بضغطة زر.
- الحذف نهائي للصفوف نفسها، لكن الأرشيف بيحتفظ ببياناتها؛ الاستعادة بتفشل لو الصف الأصلي اتعدّل بعد الحذف أو اتسجّل بيانات جديدة بنفس المعرّف.
- `supabase/reset_data.sql` مسؤول عن مسح كل بيانات الأعمال **والأرشيف** والبدء من جديد مع الاحتفاظ بحسابات الدخول — راجع التحذيرات جوه الملف قبل تشغيله.
- للتأكد إن كل الدوال والجداول (بما فيها الحذف/الاستعادة) مطبّقة، شغّل `supabase/verify_migrations.sql` في SQL Editor وراجع نتائج `OK` / `MISSING`.
- الصلاحيات المعروضة عند تخصيص مستخدم مقسّمة: 12 صلاحية مهمة ظاهرة، و19 صلاحية إضافية/حساسة مخفية تحت زر «عرض صلاحيات إضافية». القائمة الكاملة (31) وافتراضيات الأدوار على السيرفر لم تتغير — التجميع للعرض فقط.

## الأمان

- تسجيل دخول باسم مستخدم + كلمة مرور (يُخزَّن داخلياً كبريد صناعي `username@sushirolls.local` عبر Supabase Auth مع hashing).
- 9 أدوار + صلاحيات تفصيلية لكل مستخدم (تخصيص يعلو على افتراضي الدور).
- RLS على كل الجداول، دوال أوردرات/مخزون/ورديات `security definer` مع فحص صلاحيات، وسجل تدقيق (audit) للعمليات المالية.
- الإلغاء والاسترداد بآثار تدقيق. يمكن لمالك/السوبر أدمن حذف الصفوف نهائياً من صفحة «إدارة الحذف والاستعادة» بعد تفعيل `superadmin_delete.sql` + `trash.sql`؛ كل عملية موثّقة وقابلة للاستعادة من الأرشيف ما لم يتعارض المعرّف مع بيانات جديدة.
- انتهاء جلسة تلقائي قابل للضبط من الإعدادات.

## بنية المشروع

```
src/main        عملية Electron الرئيسية (نافذة آمنة، طباعة، ملفات، إعدادات)
src/preload     جسر IPC المحدود
src/renderer    واجهة React (صفحات، مكونات، هوية بصرية، تكامل Supabase)
src/shared      عقود IPC والمفاتيح المشتركة
supabase        schema.sql + migrations/ + functions/admin-users + functions/device-sync + tests
zkteco-bridge   خدمة ويندوز للتواصل مع أجهزة البصمة (بروتوكول Pipe + outbox)
scripts         فحوص البناء (منها check-migrations.mjs)
tests           اختبارات الحسابات المالية والصلاحيات
```
